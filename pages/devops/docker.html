Module 1 : Conteneurs Lecon 1/10 35 min Facile

Containerisation vs Virtualisation

La containerisation et la virtualisation sont deux approches differentes pour isoler des applications et leurs dependances. Comprendre leurs differences fondamentales est essentiel pour architecturer correctement son infrastructure.

Virtualisation classique

La virtualisation classique repose sur un hyperviseur (Type 1 comme VMware ESXi, ou Type 2 comme VirtualBox) qui cree des machines virtuelles completes. Chaque VM possede son propre systeme d exploitation (OS) complet, son noyau, ses pilotes et ses bibliothèques. Cela permet une isolation totale mais entraine une surcharge (overhead) importante en termes de ressources (RAM, CPU, stockage) et de temps de demarrage (plusieurs minutes).

  • Avantages : isolation complete, compatibilite avec n importe quel OS, securite renforcee grace a l isolation du noyau.
  • Inconvenients : consommation de ressources elevee (chaque VM tourne un OS complet), demarrage lent (boot complet requis), images volumineuses (plusieurs Go).

Containerisation avec Docker

Docker utilise la virtualisation au niveau du noyau (OS-level virtualisation). Les conteneurs partagent le noyau de l hote mais s execute dans des espaces de noms (namespaces) isoles. Chaque conteneur n inclut que l application, ses dependances et ses bibliothèques, sans OS complet. C est pourquoi les conteneurs demarrent en quelques secondes et sont extremement legers (quelques Mo).

  • Avantages : demarrage ultra-rapide (millisecondes a secondes), faible overhead ressources, images legere (Mo vs Go), portabilite excellente, integration native avec CI/CD.
  • Inconvenients : partage du noyau (moins isole qu une VM), tous les conteneurs tournent sur le meme OS (Linux principalement), la securite depend de la configuration du noyau.
En resume : Les VM offrent une isolation complete mais sont lourdes. Les conteneurs sont legers et rapides mais partagent le noyau. En pratique, on utilise souvent les deux ensemble : les conteneurs dans des VMs pour combiner la portabilite de Docker avec l isolation de la virtualisation. Kubernetes tourne typiquement sur des VMs (AWS EC2, GCP Compute Engine) qui hebergent des conteneurs.

Dockerfile : Construire ses images

Le Dockerfile est un fichier texte qui contient les instructions pour construire une image Docker. Chaque instruction cree un calque (layer) dans l image. Les instructions sont executees sequentiellement et chaque calque est mis en cache pour accelerer les reconstructions futures.

Instructions essentielles

FROM python:3.11-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 8000
CMD ["python", "main.py"]

FROM definit l image de base. Toujours commencer par une image officielle et minimale. Les variantes slim ou alpine sont plus petites (quelques dizaines de Mo vs plusieurs centaines). WORKDIR definit le repertoire de travail. COPY copie les fichiers de l hote vers le conteneur. RUN execute une commande pendant la construction (installation de paquets, compilation). EXPOSE documente les ports utilises (ne les ouvre pas reels). CMD definit la commande par defaut au demarrage du conteneur.

ENTRYPOINT vs CMD

CMD peut etre ecrase par l utilisateur lors du demarrage : docker run mon-image autremode. ENTRYPOINT configure le conteneur comme un executable. Les arguments passes a docker run sont ajoutes a l entree. On utilise souvent les deux ensemble : ENTRYPOINT definit l executble, CMD fournit les arguments par defaut.

ENTRYPOINT ["python"]
CMD ["main.py"]

Cette configuration permet de lancer docker run mon-image pour executer python main.py, ou docker run mon-image test.py pour executer python test.py.

Multi-stage builds

Les multi-stage builds sont essentiels pour creer des images de production optimisees. L idee est d utiliser une image complete pour compiler ou construire, puis de copier uniquement les artefacts dans une image minimale pour la production.

FROM golang:1.21 AS builder
WORKDIR /src
COPY . .
RUN go build -o /app

FROM alpine:3.18
COPY --from=builder /app /app
CMD ["/app"]

L image finale ne contient que l executable compile et l image alpine (5 Mo), sans les outils de compilation (几百 Mo). Cela reduit significativement la taille de l image et la surface d attaque.

Bonnes pratiques Dockerfile : 1) Ordonner les instructions du moins changeable au plus changeable (COPY requirements.txt avant COPY .). 2) Utiliser .dockerignore pour exclure fichiers inutiles. 3) Ne jamais stocker de secrets dans les layers (utiliser des variables d environnement ou des secrets Docker). 4) Utiliser des images officielles et verified publishers. 5) Fixer les versions des dependances pour la reproductibilite.

Images, Layers et Cache

Une image Docker est un modele en lecture seule qui contient tout ce dont un conteneur a besoin pour s executer. Les images sont construites a partir de calques (layers) empiles. Chaque instruction du Dockerfile cree un nouveau calque.

Le systeme de cache

Docker utilise un systeme de cache intelligent pour accelerer la construction des images. Si un calque et ses dependances n ont pas change, Docker reutilise le calque en cache au lieu de le recreer. C est pourquoi l ordre des instructions dans le Dockerfile est crucial : il faut placer les instructions les moins frequentement changees en premier.

Par exemple, si vous modifiez le code source mais pas les dependances, Docker reutilisera le calque d installation des paquets et ne reconstruira que les calques ulterieurs. La commande docker build --no-cache force la reconstruction complete sans utiliser le cache.

Optimisation des images

  • Images de base minimales : utiliser python:3.11-slim au lieu de python:3.11, ou alpine au lieu de ubuntu.
  • Combinaison de RUN : grouper plusieurs commandes RUN en une seule pour reduire le nombre de calques et la taille totale.
  • Clean-up dans RUN : nettoyer les caches et fichiers temporaires dans la meme instruction RUN (car chaque RUN est un calque independant).
  • Multi-stage builds : separer la phase de build de la phase de production pour exclure les outils de developpement de l image finale.
  • .dockerignore : exclure les fichiers non necessaires (node_modules, .git, __pycache__, tests) pour accelerer la copie et reduire la taille.
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json .
RUN npm ci --only=production
COPY . .
RUN npm run build

FROM nginx:alpine
COPY --from=builder /app/dist /usr/share/nginx/html
EXPOSE 80

Containers et Lifecycle

Un conteneur Docker est une instance en cours d execution d une image. Il est ephemere par defaut : toutes les donnees ecrites dans le conteneur sont perdues lorsqu il est supprime. Comprendre le cycle de vie d un conteneur est fondamental pour gerer correctement les applications.

Le cycle de vie

Un conteneur passe par plusieurs etapes : Created (cree mais pas demarre), Running (en cours d execution), Paused (suspendu avec SIGSTOP), Stopped (arrete proprement avec SIGTERM puis SIGKILL), Deleted (supprime). Les commandes docker start, docker stop, docker pause, docker rm controlent ces transitions.

Namespaces et cgroups

Docker repose sur deux mecanismes du noyau Linux pour l isolation :

  • Namespaces : chaque conteneur a son propre espace pour les processus (PID), le reseau (NET), les systemes de fichiers (MNT), les utilisateurs (USER), et le hostname (UTS). Un processus dans un conteneur ne voit que les autres processus de ce conteneur.
  • cgroups (Control Groups) : limitent et isolent les ressources (CPU, RAM, E/S) allouees a un conteneur. Un conteneur ne peut pas consommer plus de ressources que ce qui est defini, empechant ainsi qu une application monopolise les ressources de l hote.

Commandes essentielles du lifecycle

docker run -d --name web -p 8080:80 nginx
docker ps                          # conteneurs en cours
docker ps -a                       # tous les conteneurs
docker stop web                     # arret propre (SIGTERM)
docker start web                    # redemarrer
docker restart web                  # arreter puis demarrer
docker logs web                     # voir les logs
docker exec -it web sh              # shell interactif
docker rm web                       # supprimer (arrete)
docker rm -f web                    # supprimer (force)
docker inspect web                  # details complets
docker stats web                    # usage CPU/RAM en temps reel
Important : Les conteneurs sont ephemeres par design. Ne jamais stocker de donnees persistantes (bases de donnees, fichiers uploades) dans le systeme de fichiers d un conteneur. Utilisez toujours des volumes pour les donnees qui doivent survivre a l arret ou a la suppression du conteneur.

Volumes et Persistence

Les volumes sont le mecanisme Docker pour persister les donnees au-dela du cycle de vie des conteneurs. Ils sont geres par Docker et stockes dans un repertoire special sur l hote (/var/lib/docker/volumes/).

Types de persistance

  • Volumes : stockes par Docker, geres par docker volume create. Meilleure option pour les donnees persistantes (bases de donnees). Isolation du systeme de fichiers hote.
  • Bind Mounts : montent un repertoire de l hote directement dans le conteneur. Utile en developpement pour monter le code source en temps reel.
  • tmpfs : stocke en memoire RAM uniquement. Pour les donnees sensibles qui ne doivent jamais etre sur disque.
# Volume nomme
docker volume create pgdata
docker run -v pgdata:/var/lib/postgresql/data postgres

# Bind mount
docker run -v /chemin/local:/app/data nginx

# En lecture seule
docker run -v /chemin/local:/app/config:ro nginx

# Creation automatique
docker run --mount type=volume,source=pgdata,target=/var/lib/postgresql/data postgres

Reseaux Docker

Docker fournit plusieurs drivers reseau pour connecter les conteneurs entre eux et avec l exterieur. Le bon choix depend de l architecture de l application.

Drivers reseau

  • bridge (defaut) : cree un reseau prive sur l hote. Les conteneurs sur le meme bridge peuvent communiquer. Ideal pour un seul hote.
  • host : le conteneur partage directement le reseau de l hote. Pas d isolation reseau, mais performance maximale.
  • overlay : permet la communication entre conteneurs sur des hotes differents. Utilise avec Docker Swarm ou Kubernetes.
  • none : aucun reseau. Le conteneur est completement isole.
docker network create mon-reseau
docker run -d --name app1 --network mon-reseau nginx
docker run -d --name app2 --network mon-reseau alpine ping app1

Sur le meme reseau, les conteneurs se comunicent via leur nom comme hostname (app1, app2). C est le mecanisme de DNS interne de Docker.

Docker Compose

Docker Compose est un outil pour definir et orchestrer des applications multi-conteneurs via un fichier YAML. Il est ideal pour les environnements de developpement, les tests, et les deploiements simples.

Exemple de fichier docker-compose.yml

version: "3.9"
services:
  web:
    build: .
    ports:
      - "8080:80"
    depends_on:
      - api
    networks:
      - frontend

  api:
    image: node:20-alpine
    working_dir: /app
    volumes:
      - ./api:/app
    command: npm start
    environment:
      - DB_HOST=postgres
      - DB_PORT=5432
    networks:
      - frontend
      - backend

  postgres:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: myapp
      POSTGRES_USER: admin
      POSTGRES_PASSWORD: secret
    volumes:
      - pgdata:/var/lib/postgresql/data
    networks:
      - backend

volumes:
  pgdata:

networks:
  frontend:
  backend:

Commandes compose essentielles

docker compose up -d           # demarrer en arriere-plan
docker compose down            # arreter et supprimer
docker compose logs -f api     # suivre les logs
docker compose ps              # etat des services
docker compose exec api sh     # shell dans un service
docker compose build --no-cache # reconstruire sans cache
docker compose pull            # telecharger les images
docker compose restart api     # redemarrer un service
Compose v2 : La version 2 de Docker Compose est integree en tant que plugin Docker (docker compose sans tiret) au lieu d un binaire separe (docker-compose). Elle supporte les profiles, les healthchecks, et une meilleure gestion des secrets.

Bonnes Pratiques et Securite

La securite des conteneurs Docker est un sujet critique en production. Voici les pratiques essentielles pour deployer des conteneurs de maniere securisee.

  • Ne jamais tourner en root : creer un utilisateur dedie dans le Dockerfile avec USER et donner les permissions necessaires. Un conteneur root peut s echapper et compromettre l hote.
  • Images minimales : utiliser des images slim ou alpine pour reduire la surface d attaque. Moins de binaires signifie moins de vulnerabilites potentielles.
  • Scanner les vulnerabilites : utiliser docker scout, trivy, ou snyk pour scanner les images avant le deploiement.
  • Secrets management : ne jamais hardcoder de mots de passe ou cles API dans les Dockerfiles ou les images. Utiliser Docker Secrets, des variables d environnement, ou des outils comme HashiCorp Vault.
  • Read-only filesystem : utiliser --read-only pour empecher l ecriture dans le conteneur, en montant les repertoires necessaires en volumes.
  • Resource limits : toujours definir --memory et --cpus pour eviter qu un conteneur ne consomme toutes les ressources de l hote.
  • Network policies : isoler les reseaux et ne connecter que les conteneurs qui doivent communiquer.
docker run -d --name app \
  --read-only \
  --tmpfs /tmp \
  --user 1000:1000 \
  --memory 512m \
  --cpus 1.0 \
  --cap-drop ALL \
  --cap-add NET_BIND_SERVICE \
  nginx

Questions d entretien frequentes

Q1 : Quelle est la difference entre CMD et ENTRYPOINT dans un Dockerfile ?

CMD definit la commande par defaut qui peut etre ecrasee lors du docker run (ex: docker run image alire). ENTRYPOINT configure le conteneur comme un executable dont les arguments passes a docker run sont ajoutes. On utilise souvent les deux ensemble : ENTRYPOINT pour l executable principal, CMD pour les arguments par defaut. Par exemple, ENTRYPOINT ["python"] et CMD ["app.py"] permet de lancer python app.py par defaut, ou python autre chose si on passe un argument.

Q2 : Comment fonctionne le cache des couches Docker et comment l optimiser ?

Docker cache chaque couche (instruction) d un Dockerfile. Si la couche et ses dependances n ont pas change, Docker reutilise le cache. Pour optimiser, placez les instructions les moins changeables en premier (FROM, installation de systeme), puis les dependances (COPY requirements.txt, RUN pip install), et enfin le code source (COPY .). Utilisez --no-cache pour forcher la reconstruction. Les multi-stage builds reduisent aussi la taille finale en excluant les outils de build.

Q3 : Quand utiliser un volume Docker vs un bind mount ?

Volume Docker : pour les donnees persistantes en production (bases de donnees, backups). Gere par Docker, portable, supporte les drivers de stockage (NFS, cloud). Bind mount : pour le developpement local (monter le code source en temps reel). Plus simple mais depend de la structure de l hote, pas portable. tmpfs : pour les secrets ou donnees temporaires en memoire uniquement.

Q4 : Un conteneur Docker est-il aussi isole qu une machine virtuelle ?

Non. Les conteneurs partagent le noyau Linux de l hote, ce qui signifie qu une vulnerabilite du noyau peut potentiellement permettre une echappatoire (container escape). Les VMs ont un noyau完全 isole. En pratique, on combine les deux : les conteneurs dans des VMs, avec des measures de securite comme seccomp, AppArmor, SELinux, et --cap-drop pour reduire les privileges. Kubernetes utilise souvent des sandboxing comme gVisor ou Kata Containers pour renforcer l isolation.

Q5 : Comment reduire la taille d une image Docker de production ?

1) Utiliser des images de base minimales (alpine, slim, distroless). 2) Multi-stage builds pour exclure les outils de build. 3) Combinaison des RUN pour reduire les couches. 4) Nettoyage des caches dans la meme instruction RUN. 5) .dockerignore pour exclure fichiers inutiles. 6) Supprimer les outils de debug de production. 7) Docker Slim ou docker-slim pour l optimisation automatique. Une image node optimisee peut passer de 900 Mo a moins de 50 Mo.
