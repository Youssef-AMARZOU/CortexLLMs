Load Balancing

Module 1 : Concepts Fondamentaux Lecon 1/10 30 min Facile

Pourquoi le Load Balancing

Le load balancing (equilibrage de charge) est un mecanisme fondamental de l architecture distribuee. Il consiste a repartir le trafic entrant sur plusieurs serveurs (backend) pour garantir la disponibilite, la performance et la fiabilite d une application.

Les problemes resolus

  • Scalabilite : un seul serveur a une capacite limitee. En ajoutant des serveurs et en repartissant la charge, on augmente le debit (throughput) total du systeme. Le load balancer est le point d entree unique (single point of entry) qui route le trafic vers le serveur le moins charge.
  • Haute disponibilite : si un serveur tombe, le load balancer detecte la panne via des health checks et redirige automatiquement le trafic vers les serveurs restants. Aucune intervention manuelle n est necessaire, assurant une disponibilite continue.
  • Performance : en repartissant les requetes sur plusieurs serveurs, on reduit la latence moyenne et on evite les goulots d etranglement. Les requetes sont traitees plus rapidement car chaque serveur a moins de charge.
  • Maintenabilite : on peut mettre a jour, remplacer ou ajouter des serveurs sans downtime en les retirant ou ajoutant du pool du load balancer de maniere transparente pour les utilisateurs.

Quand utiliser un load balancer ?

Le load balancing est necessaire des que l application depasse les capacites d un seul serveur ou que la haute disponibilite est requise. Pour les petites applications, un seul serveur avec un bon dimensionnement suffit. Pour les applications a trafic eleve, les services critiques, et les architectures microservices, le load balancer est un composant incontournable.

Point cl : Le load balancer est le premier composant que les utilisateurs rencontrent dans l architecture. Il agit comme le reverse proxy : les clients se connectent au load balancer, qui transmet les requetes aux serveurs backend et retourne les reponses. Les clients ne voient jamais les serveurs reels, ce qui ajoute une couche d abstraction et de securite.

Algorithmes de Distribution

Le choix de l algorithme de distribution est crucial et depend du type de trafic, des besoins en session, et descaracteristiques des serveurs backend.

Round Robin

L algorithme le plus simple : les requetes sont distribuees sequentiellement aux serveurs dans un ordre circulaire. La premiere requete va au serveur 1, la deuxieme au serveur 2, etc. Quand on arrive au dernier serveur, on recommence au premier.

  • Avantages : implementation tres simple, equitable si tous les serveurs ont la meme puissance, pas besoin de stocker d etat.
  • Inconvenients : ne tient pas compte de la charge actuelle des serveurs ni de leur capacite. Si un serveur est plus lent ou a plus de travail, il recevra autant de requetes qu un serveur libre.

Weighted Round Robin

Variante du Round Robin ou chaque serveur a un poids proportionnel a sa capacite. Un serveur avec un poids de 3 recevra 3 fois plus de requetes qu un serveur avec un poids de 1. Utile quand les serveurs ont des configurations materielles differentes.

Least Connections

Chaque requete est envoyee au serveur qui a le moins de connexions actives au moment du traitement. C est un algorithme adaptatif qui s ajuste automatiquement a la charge reelle.

  • Avantages : gere mieux les requetes a duree variable (certaines requetes sont plus longues que d autres), s adapte aux pics de charge.
  • Inconvenients : necessite de suivre le nombre de connexions pour chaque serveur (overhead memoire), peut etre plus lent que Round Robin.

IP Hash

Un hash de l adresse IP du client determine quel serveur recevra la requete. Le meme client sera toujours route vers le meme serveur, ce qui garantit la persistance de session (sticky sessions) sans stocker d etat cote load balancer.

  • Avantages : pas besoin de stocker les sessions cote load balancer, compatible avec les applications qui stockent l etat en memoire (sessions Redis, cache local).
  • Inconvenients : repartition desequilibree si certaines plages IP ont plus de trafic. Un serveur tombe = toutes les sessions de ses clients sont perdues. Problem NAT (beaucoup de clients derriere la meme IP).
En pratique : Le Least Connections est souvent le meilleur choix general. Le Round Robin suffit pour des serveurs identiques et des requetes uniformes. L IP Hash est reserve aux applications avec sessions en memoire qu on ne peut pas externaliser. Pour les architectures modernes, on externalise les sessions (Redis, Memcached) et on utilise Least Connections ou des algorithmes plus avances.

Consistent Hashing

Le consistent hashing est un algorithme specialise pour minimiser les reassignments quand les serveurs sont ajoutes ou retires du pool. C est essentiel pour les systemes de cache distribue et les bases de donnees shardees.

Le probleme du hash simple

Avec un hash classique (hash(cle) % N), quand on ajoute ou retire un serveur (N change), presque toutes les cles sont reassignees a de nouveaux serveurs. Cela provoque un stampede (tempete) de requetes vers les nouveaux serveurs et une invalidation massive des caches, ce qui peut entrainer un effondrement du systeme (thundering herd).

L anneau de hashing

Le consistent hashing place les serveurs et les cles sur un anneau virtuel (0 a 2^32). Pour trouver le serveur d une cle, on hash la cle et on suit l anneau dans le sens horaire jusqu a trouver le premier serveur. Quand un serveur est ajoute ou retire, seules les cles entre le serveur modifie et son voisin dans le sens antihoraire sont reassignees. En moyenne, seul 1/N des cles est deplace.

Virtual Nodes (VNodes)

L anneau de base peut creer des desequilibres si les serveurs ne sont pas uniformement repartis. Les virtual nodes resolvent ce probleme en plaçant chaque serveur physique a plusieurs positions sur l anneau (ex: 150 vnodes par serveur). Cela ameliore la distribution et rend le systeme plus robuste aux ajouts/retires de serveurs.

Position = hash(serveur_id + "#" + vnode_numero)

Netflix利用这个概念 avec Cassanda et DynamoDB. Chaque partition de donnees est attribuee a un serveur en suivant l anneau. Les vnodes garantissent une distribution quasi-uniforme meme avec un petit nombre de serveurs physiques.

Utilisation re : Le consistent hashing est utilise dans Amazon DynamoDB, Apache Cassandra, Memcached, Discord, et CDNs comme Cloudflare. C est un concept incontournable pour les systemes distribues qui necessitent une distribution efficace des donnees avec un minimum de reassignments lors des changements de topologie.

Load Balancing Niveau 4 vs Niveau 7

Le load balancing peut intervenir a differentes couches du modele OSI. Les deux plus courants sont le L4 (couche transport) et le L7 (couche application).

Load Balancing L4 (Transport)

Le load balancer L4 opere au niveau des paquets TCP/UDP sans inspecter le contenu applicatif. Il route le trafic en se basant sur l adresse IP source/destination et les numeros de port. C est plus rapide car il n y a pas d analyse du contenu HTTP.

  • Avantages : tres performant (forwarding simple, pas de dechiffrage SSL), latence minimale, compatible avec tout protocole TCP/UDP.
  • Inconvenients : pas de routing base sur le contenu (URL, headers, cookies), impossible de faire du content-based routing.
  • Usage : databases, jeux en ligne, streaming video, microservices internes.

Load Balancing L7 (Application)

Le load balancer L7 interprete le protocole HTTP/HTTPS. Il peut inspecter les headers, les cookies, les URLs, les corps de requete, et prendre des decisions de routing sophistiquees.

  • Avantages : routing base sur le contenu (API v1 vs v2), SSL termination (decryptage HTTPS), compression, cache, protection contre les attaques DDoS, logging detaille.
  • Inconvenients : plus lent (inspection du contenu requis), consomme plus de ressources, necessite de decrypter le trafic HTTPS (potentiel risque de securite).
  • Usage : applications web, API REST, GraphQL, microservices avec routing base sur le path.
Architecture moderne : En pratique, on utilise souvent un L4 devant un L7. Le L4 (ex: AWS Network Load Balancer) gere le trafic brut a grande vitesse. Le L7 (ex: AWS Application Load Balancer) gere le routing intelligent. Ce couple offre la performance du L4 avec la flexibilite du L7.

Health Checks

Les health checks sont des mecanismes permettant au load balancer de verifier periodiquement que les serveurs backend sont en bonne sante et capables de traiter des requetes. Sans health checks, le load balancer continuerait a envoyer du trafic a des serveurs en panne, degradant l experience utilisateur.

Types de health checks

  • TCP Health Check : verifie simplement qu une connexion TCP peut etre etablie sur le port specifie. Rapide mais ne garantit pas que l application fonctionne reellement.
  • HTTP Health Check : effectue une requete HTTP GET sur un endpoint dedie (ex: /health ou /status) et verifie que le code de retour est 200 OK. Plus fiable car il verifie que l application repond correctement.
  • HTTPS Health Check : meme chose que HTTP mais avec SSL/TLS. Verifie aussi le certificat.
  • Custom Health Check : execute une logique metier specifique (verifier la connexion a la base de donnees, la disponibilite du cache, etc.).

Parametres importants

  • Interval : frequence des verifications (ex: toutes les 10 secondes). Trop frequent = overhead. Trop rare = delai de detection.
  • Timeout : delai maximum d attente de reponse (ex: 5 secondes). Si pas de reponse, le serveur est declare down.
  • Unhealthy threshold : nombre d echecs consecutifs avant de retirer le serveur (ex: 3 echecs).
  • Healthy threshold : nombre de succes consecutifs avant de remettre le serveur dans le pool (ex: 2 succes).
Bonnes pratiques : 1) Creer un endpoint /health dedie qui verifie les dependances critiques (DB, cache). 2) Le health check doit etre leger et rapide. 3) Ne pas envoyer le health check dans les logs de l application pour eviter le bruit. 4) Utiliser des seuils d echec et de succes separes pour eviter le flip-flopping (ajout/retrait repetitif d un serveur).

Outils de Load Balancing

Nginx

Nginx est le load balancer open source le plus populaire au monde. Il est extremement performant et polyvalent, servant a la fois de reverse proxy, de load balancer, et de serveur web.

upstream backend {
    least_conn;
    server 192.168.1.10:8080 weight=3;
    server 192.168.1.11:8080 weight=2;
    server 192.168.1.12:8080 backup;
    keepalive 32;
}

server {
    listen 80;
    location / {
        proxy_pass http://backend;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_connect_timeout 5s;
        proxy_read_timeout 30s;
    }
}

Nginx supporte les algorithmes round-robin (defaut), least_conn, et ip_hash. La directive keepalive maintient des connexions persistantes avec les serveurs backend pour reduire la latence.

HAProxy

HAProxy est un load balancer L4/L7 tres performant, specialement concu pour le load balancing. Il est utilise par GitHub, Stack Overflow, et Reddit. Ses forces sont sa vitesse, sa fiabilite, et ses fonctionnalites avancees de health checking et de logging.

frontend http_front
    bind *:80
    default_backend servers

backend servers
    balance leastconn
    option httpchk GET /health
    server s1 192.168.1.10:8080 check inter 5s fall 3 rise 2
    server s2 192.168.1.11:8080 check inter 5s fall 3 rise 2
    server s3 192.168.1.12:8080 check backup

Load Balancers Cloud

  • AWS ALB (Application Load Balancer) : load balancer L7 avec routing base sur le path, le host, et les headers. Supporte WebSocket, HTTP/2, et SSL termination automatique.
  • AWS NLB (Network Load Balancer) : load balancer L4 ultra-performant (millions de requetes/s). Latence fixe, ideal pour les applications en temps reel.
  • GCP Cloud Load Balancing : load balancer L7 global avec CDN integre, protection DDoS, et SSL automatique.
  • Azure Load Balancer : load balancer L4 avec health checks et failover automatique.

Architecture Single Tier vs Dual Tier

Single Tier (Couche Unique)

Dans cette architecture, un seul load balancer (ou un cluster actif-passif) gere tout le trafic. C est la configuration la plus simple et la plus courante pour les applications a trafic modere.

  • Avantages : simple a configurer et a maintenir, cout reduit, latence minimale (un seul saut).
  • Inconvenients : point unique de depannage (single point of failure) si le load balancer n est pas en cluster, limite de scalabilite si le trafic depasse la capacite du LB.
  • Usage : applications monolithiques, sites web a trafic modere, environnements de developpement.

Dual Tier (Double Couche)

Deux niveaux de load balancing : un L4 en premiere couche pour distribuer le trafic brut, puis un L7 en deuxieme couche pour le routing intelligent. C est l architecture standard pour les applications a trafic eleve.

  • Avantages : haute disponibilite (pas de single point of failure), performance optimisee (L4 rapide + L7 intelligent), scalabilite horizontale.
  • Inconvenients : plus complexe a configurer, cout plus eleve, plus de points de monitoring.
  • Usage : applications critiques, e-commerce, plateformes SaaS, architectures microservices.
Architecture recommandee : Pour les applications de production, utilisez au minimum un load balancer en configuration active-passive (deux instances). Pour les architectures critiques, combinez un L4 (AWS NLB, Keepalived) avec un L7 (Nginx, HAProxy, AWS ALB). Ajoutez un DNS geographique (Route53, Cloudflare) pour le routing global et la haute disponibilite multi-region.

Questions d entretien System Design

Q1 : Comment gerer les sessions utilisateur derriere un load balancer ?

Trois approches : 1) Sticky sessions (IP Hash) : toujours router le meme client vers le meme serveur. Simple mais pas scalable et problématique si le serveur tombe. 2) Session externalisee : stocker les sessions dans Redis ou Memcached, accessible par tous les serveurs. C est la meilleure approche car elle est scalable et fault-tolerant. 3) Sans etat (stateless) : utiliser des JWT (JSON Web Tokens) stockes cote client. Aucune session cote serveur, le serveur verifie juste le token. Le plus scalable.

Q2 : Qu est-ce que le round-robin DNS et pourquoi est-ce different d un load balancer ?

Le round-robin DNS resout un nom de domaine vers plusieurs adresses IP, et les clients choisissent aleatoirement. C est different d un load balancer car : 1) Le DNS ne fait pas de health checking (un serveur down continuera a recevoir du trafic). 2) Le TTL du DNS cree des problemes de propagation. 3) Pas de sticky sessions. 4) Le client choisit, pas le serveur. C est une solution rudimentaire pour des cas simples, mais un vrai load balancer est toujours preferable en production.

Q3 : Comment gerer le SSL/TLS dans une architecture avec load balancer ?

L approche standard est la SSL termination au niveau du load balancer : le LB dechiffre le HTTPS entrant et transmet le trafic en HTTP aux serveurs backend (dans un reseau prive). Avantages : centralise la gestion des certificats, libere les serveurs backend du chiffrement, permet l inspection du trafic (L7 routing). Inconvenients : le trafic interne n est pas chiffre. Solution : le SSL re-encryption rechiffre le trafic entre le LB et les backends pour une securite end-to-end.

Q4 : Comment le load balancing gere-t-il les pics de trafic soudains ?

Le load balancer seul ne suffit pas. Il faut combiner : 1) Auto-scaling : ajout automatique de serveurs quand la charge depasse un seuil. 2) Queuing : files d attente (RabbitMQ, SQS) pour absorber les pics. 3) Rate limiting : limiter le nombre de requetes par client pour eviter les abus. 4) Circuit breaker : arreter temporairement les requetes vers un serveur en surcharge. 5) CDN : cache du contenu statique pour reduire la charge sur le LB. Le load balancer distribue le trafic, mais c est l auto-scaling qui augmente la capacite.

Q5 : Quelle est la difference entre actif-passif et actif-actif pour un load balancer ?

Actif-passif : un LB traite tout le trafic, l autre est en standby pret a prendre le relais en cas de panne (failover). Avantage : simplicite, pas de conflits. Inconvenient : ressources sous-utilisees. Actif-actif : les deux LB traitent le trafic en meme temps, partageant la charge. Avantage : meilleure utilisation des ressources, scalabilite. Inconvenient : necessite une synchronisation d etat complexe (sessions, connexions). En cloud, on utilise souvent des load balancers manages (ALB, NLB) qui gerent automatiquement la haute disponibilite en mode actif-actif.
