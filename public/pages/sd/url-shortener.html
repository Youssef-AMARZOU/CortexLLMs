Conception d'un URL Shortener

Conception Lecon 1 / 10 Temps de lecture: ~30 min

1. Requirements

Un URL Shortener est un systeme qui transforme une URL longue en une URL courte et facile a partager. Des services comme Bitly, TinyURL et t.co gerent des milliards de redirections quotidiennes. Ce cas d'etude est un classique de l'entretien System Design car il couvre presque tous les concepts fondamentaux: design de base de donnees, caching, hashing, load balancing et strategies de scaling.

Requirements Fonctionnelles

  • Creer un raccourci: L'utilisateur fournit une URL longue, le systeme genere et retourne une URL courte unique.
  • Rediriger: Lorsqu'un utilisateur visite l'URL courte, il est redirige vers l'URL originale.
  • Personnalisation: (Optionnel) L'utilisateur peut choisir le raccourci au lieu d'un genere automatiquement.
  • Expiration: Les URLs courtes peuvent avoir une date d'expiration optionnelle.
  • Analytics: Nombre de clics, sources, localisation geographique, appareils.

Requirements Non-Fonctionnelles

  • Haute disponibilite: Le systeme doit etre disponible 99,99% du temps. Une redirection cassee signifie des liens casse partout.
  • Latence faible: La redirection doit etre extremement rapide (moins de 10ms) car elle ajoute un saut supplementaire avant le contenu reel.
  • Echelle massive: Supporter 100 millions de creations et 10 milliards de redirections par mois.
  • Court raccourci: Les URLs courtes doivent etre vraiment courtes (6-7 caracteres max).
  • Unicite: Chaque URL longue doit mapper vers une URL courte unique, et chaque URL courte doit etre unique.
Estimation de Capacite

10 milliards de redirections/mois = environ 3 700 redirections/seconde. 100 millions de creations/mois = environ 40 creations/seconde. Ratio lecture/ecriture: 100:1 (beaucoup plus de redirections que de creations). Stockage: 500 caracteres/URL longue + 7 caracteres URL courte + metadonnees = environ 1KB par entree. 100 millions/mois x 5 ans = 6 milliards d'entrees = environ 6 To de stockage brut.

301 vs 302

Le code 301 (Moved Permanently) indique au navigateur de mettre en cache la redirection, ce qui reduit les requetes vers notre serveur mais empeche le tracking. Le code 302 (Found) force le navigateur a revenir vers notre serveur a chaque fois, permettant le tracking mais augmentant la charge. La plupart des URL shorteners utilisent le 302.

3. Strategie de Hachage

La partie centrale d'un URL Shortener est la generation du code court (short code) a partir de l'URL longue. Il existe plusieurs approches, chacune avec des compromis differents en termes de performance, d'unicite et de complexite.

MD5/SHA256 + Base62

On applique une fonction de hash (MD5 ou SHA256) a l'URL longue, puis on convertit le resultat en base62 (a-z, A-Z, 0-9) pour obtenir un code court. MD5 produit un hash de 128 bits, ce qui donne environ 22 caracteres en base62. On peut tronquer a 7 caracteres pour obtenir un code plus court.

function generateShortCode(url) {
    const hash = md5(url);
    const alphabet = 'abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789';
    let code = '';
    let num = BigInt('0x' + hash.substring(0, 12));
    for (let i = 0; i < 7; i++) {
        code = alphabet[Number(num % 62n)] + code;
        num = num / 62n;
    }
    return code;
}

console.log(generateShortCode('https://example.com/long/path'));
// Resultat: "xK9mZp2"
Collisions

Avec 7 caracteres en base62, on a 62^7 = environ 3,5 trillions de combinaisons possibles. Pour 1 milliard d'URLs, la probabilite de collision est d'environ 0,03% (loi des birthday). En cas de collision, on regenere un nouveau code. Avec un compteur atomique, les collisions sont impossiblees.

Counter-Based (Compteur Serveur)

Un compteur atomique genere un numero unique a chaque requete. Ce numero est converti en base62. C'est le systeme le plus simple et le plus fiable: aucune collision possible, codes sequentiels et previsibles.

class ShortCodeGenerator {
    constructor() {
        this.counter = 0;
        this.alphabet = 'abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789';
    }
    generate() {
        this.counter++;
        return this.toBase62(this.counter);
    }
    toBase62(num) {
        let result = '';
        while (num > 0) {
            result = this.alphabet[num % 62] + result;
            num = Math.floor(num / 62);
        }
        return result.padStart(7, 'a');
    }
}

Pre-Generated Keys

Une approche encore plus rapide consiste a pre-generer des millions de codes courts et a les stocker dans une file d'attente (Redis List). A chaque requete de creation, on dequeue un code. Cette approche est utilisee par les systemes a tres haute vitesse comme t.co de Twitter.

4. Design de la Base de Donnees

Le choix de la base de donnees est critique pour un URL Shortener. Le pattern d'acces est extremement asymetrique: 99% des operations sont des lectures (redirections) et seulement 1% sont des ecritures (creations).

SQL vs NoSQL

Pour un URL Shortener, une base NoSQL comme DynamoDB, Cassandra ou MongoDB est generalement preferee. Les raisons: (1) Le schema est simple (cle-valeur), (2) La disponibilite est plus importante que la coherence stricte (eventual consistency), (3) Le sharding est naturel, (4) Les operations de lecture sont tres simples et rapides. Cependant, PostgreSQL avec un bon index peut etre performant pour des echelles moyennes.

Sharding Strategy

Le sharding est essentiel pour gerer des milliards d'entrees. La strategie la plus courante est le sharding par short_code: chaque shard gere une range de codes. Le consistent hashing peut etre utilise pour distribuer les donnees de maniere equilibree. Un autre approche est le sharding par region: les redirections sont routees vers le shard le plus proche geographiquement.

5. Architecture

L'architecture d'un URL Shortener optimise pour la performance en lecture, car les redirections sont le cas d'usage principal.

App Server retourne 301/302 avec Location header

Optimisation Read-Heavy

Le pattern cache-aside est ideal ici: pour chaque redirection, on verifie d'abord Redis (cache hit rate de 80-90% avec un bon TTL). Les 10-20% de cache miss interrogent la base de donnees. Le TTL du cache est de 24 heures pour les URLs actives, et les URLs expirees sont supprimees du cache automatiquement. En cas de panne Redis, le fallback va directement a la base de donnees avec rate limiting pour eviter de la surcharger.

6. Scaling

Le scaling horizontal est la cle pour gerer la croissance du trafic d'un URL Shortener.

Horizontal Scaling

Les serveurs d'application sont stateless, ce qui permet d'en ajouter autant que necessaire derriere le load balancer. Chaque requete est traitee de maniere independante, sans dependance a l'etat d'un serveur specifique. Le scaling est automatique via des autoscaling groups (AWS) ou Kubernetes HPA.

Database Sharding

La base de donnees est sharde par range de codes courts. Chaque shard est gere par un ensemble de noeuds avec replication. Le routing est effectue par la couche applicative ou par un proxy de base de donnees comme Vitess ou ProxySQL. Le sharding par range est simple mais peut creer des hotspots si certains codes sont plus populaires que d'autres.

Read Replicas

Pour les bases de donnees relationnelles, les read replicas permettent de repartir la charge de lecture sur plusieurs instances. Le primary gere les ecritures, tandis que les replicas servent les lectures. La replication est asynchrone, ce qui introduit un legger delai (eventual consistency), acceptable dans notre cas d'usage.

Distribution Geographique

Pour les utilisateurs mondiaux, le deploiement multi-region est essentiel. Chaque region dispose de sa propre base de donnees avec replication inter-region. Le DNS geolocalise (Route53, Cloudflare) route les utilisateurs vers la region la plus proche. Les donnees sont repliquees de maniere asynchrone entre les regions, avec une coherent eventuelle acceptee.

7. Analytics

Les analytics sont une fonctionnalite importante pour les utilisateurs d'un URL Shortener. Ils veulent savoir combien de fois leur lien a ete clique, d'ou viennent les visiteurs, et quand les clics se sont produits.

Click Tracking

Chaque redirection genere un evenement de clic qui doit etre enregistre. Les donnees collectees incluent: timestamp, adresse IP (anonymisee), user-agent (navigateur, appareil), referer (site source), pays/geolocalisation, et device type (mobile/desktop). Ces donnees sont stockees dans un systeme optimise pour les series temporelles.

Real-Time vs Batch

Pour le compteur de clics en temps reel, on utilise Redis INCR sur une cle comme clicks:abc123:2025-01-15. Pour l'agregation historique, un pipeline batch (Spark, Lambda) processe les clics toutes les heures ou tous les jours et met a jour les compteurs aggregates. Le real-time est utilise pour les dashboards en direct, le batch pour les rapports historiques.

Series Temporelles

Les donnees de clics sont naturellement des series temporelles. Les bases de donnees optimisees pour ce type de donnees incluent InfluxDB, TimescaleDB (extension PostgreSQL), et Amazon Timestream. Elles supportent l'agregation temporelle (comptage par heure, jour, mois) de maniere tres efficace.

8. Rate Limiting

Le rate limiting est essentiel pour proteger le systeme contre les abus, le spam et les attaques DDoS. Sans limites, un seul utilisateur pourrait creer des millions d'URLs et surcharger la base de donnees.

Token Bucket

Le Token Bucket est l'algorithme de rate limiting le plus courant. Chaque utilisateur dispose d'un seau de tokens qui se remplit a un rythme constant. Chaque requete consomme un token. Si le seau est vide, la requete est refusee. Cet algorithme autorise les rafales (burst) tout en limitant le debit moyen.

class TokenBucket {
    constructor(capacity, refillRate) {
        this.capacity = capacity;
        this.tokens = capacity;
        this.refillRate = refillRate;
        this.lastRefill = Date.now();
    }
    allow() {
        this.refill();
        if (this.tokens >= 1) {
            this.tokens--;
            return true;
        }
        return false;
    }
    refill() {
        const now = Date.now();
        const elapsed = (now - this.lastRefill) / 1000;
        this.tokens = Math.min(
            this.capacity,
            this.tokens + elapsed * this.refillRate
        );
        this.lastRefill = now;
    }
}

Sliding Window

Le Sliding Window compte les requetes dans une fenetre de temps glissante. Par exemple: maximum 100 creations par heure. Contrairement a la fenetre fixe, il n'y a pas de frontiere temporelle rigide, ce qui evite les pics aux bornes de la fenetre.

Limits par Utilisateur

Les limites sont appliquees par utilisateur (authentifie) et par IP (non authentifie). Un utilisateur gratuit peut avoir 10 creations/jour, un payant 1000/jour. Les limites par IP sont plus agressives pour prevenir les abus.

10. Questions d'Entretien

Q1: Comment concevriez-vous un URL Shortener capable de gerer 10 milliards de redirections par mois avec moins de 10ms de latence?

Reponse: L'architecture repose sur trois piliers: (1) Cache distribue: Un cluster Redis avec 80-90% de cache hit rate. Chaque redirection interroge Redis en premier (< 1ms), seuls les 10-20% de cache miss vont a la base de donnees. (2) Database distribuee: DynamoDB ou Cassandra avec consistent hashing pour distribuer les donnees sur des dizaines de noeuds. Chaque requete de lecture touche un seul noeud (O(1)). (3) Load balancer: HAProxy ou AWS NLB en L7 pour distribuer le trafic sur des serveurs stateless. Avec cette architecture, 99% des redirections sont traitees en moins de 5ms (cache Redis), et les 1% restants en moins de 15ms (base de donnees).

Q2: Comment eviter les collisions lors de la generation des codes courts?

Reponse: Trois approches selon les besoins: (1) Compteur atomique (Redis INCR): Le plus fiable. Le compteur est distribue et atomique, garantissant l'unicite absolue. (2) UUID + Base62: Genere un UUID unique (128 bits), le convertit en base62, et tronque. La probabilite de collision est negligeable (< 10^-18). (3) Pre-generation avec verification: On genere des codes aleatoires, on verifie l'unicite en base de donnees avant de les attribuer, et on stocke des batchs de codes pre-valides dans Redis. En cas de collision, on regenere. La premiere approche (compteur) est recommandee pour la plupart des cas d'usage.

Q3: Comment gerer les URLs expirees sans impact sur les performances?

Reponse: (1) TTL Redis: Les entrees Redis ont un TTL automatique, donc les URLs expirees sont supprimees du cache sans intervention. (2) Lazy deletion en base: Lorsqu'une redirection trouve une URL expiree, elle retourne une erreur 410 Gone et supprime l'entree de maniere lazy. (3) Cron job de nettoyage: Un job periodique supprime les URLs expirees de la base de donnees (TTL index sur expires_at). (4) Bloom filter: Pour eviter d'interroger la base pour les codes qui n'existent pas, un Bloom filter en memoire verifie rapidement si un code est potentiellement valide. Cela evite des requetes inutiles vers la base de donnees pour des codes inexistants.

Q4: Comment implementerait-vous les analytics en temps reel pour millions d'utilisateurs?

Reponse: L'architecture analytics est un pipeline event-driven: (1) Emission: Chaque redirection emet un evenement Kafka avec les metadonnees (code, timestamp, IP, user-agent). (2) Stream processing: Apache Flink ou Kafka Streams processe les evenements en temps reel, comptant les clics par code URL et par fenetre temporelle (1 min, 1h, 1j). (3) Stockage: ClickHouse ou InfluxDB stockent les metriques agregees pour les dashboards temps reel. (4) Batch: Un job Spark aggreg les donnees toutes les heures pour les rapports historiques. (5) API: L'API analytics lit depuis le cache Redis (metriques temps reel) et ClickHouse (historique). Cette architecture gere des millions d'evenements/seconde avec une latence de quelques secondes pour l'affichage en temps reel.

Q5: Comment securiser un systeme d'URL Shortening contre les abus et le spam?

Reponse: Securite multi-couches: (1) Rate limiting: Token bucket par utilisateur (10/jour gratuit, 1000/jour payant) et par IP (50/heure). (2) Validation d'URL: Verifier que l'URL est bien formatee, rejeter les scripts, les data URIs, les IP privees (SSRF), et les domaines malveillants (bloc liste). (3) Authentication: API key ou OAuth pour les creates, avec tracking des abus. (4) Monitoring: Detecter les patterns suspects (milliers de creations depuis une IP, redirections vers des domaines de phishing). (5) Expiration automatique: Les URLs non authentiquees expirent apres 30 jours pour limiter la surface d'attaque. (6) Rate limit adaptatif: Augmenter les limites progressivement pour les utilisateurs de confiance.
